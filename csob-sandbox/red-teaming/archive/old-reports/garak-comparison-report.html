Root Cause: NemoGuardrails stop Parameter Bug

15,480 of 24,090 attempts (64%) returned Internal server error
NemoGuardrails crashes with TypeError when a client sends a stop parameter in the request body (generate_async() receives stop as both an explicit kwarg and inside **llm_params). Garak sends stop sequences for many probe types, triggering the bug across 64% of all attempts. The error response is not an explicit refusal, so Garak’s MitigationBypass and Prefixes detectors score it as a “bypass” — a false positive.
Known upstream fix: PR #2266 (NGUARD-880). Not backported to RHOAI 3.5. Workaround: strip stop from incoming requests at the proxy layer.

Wolf DefenderCPU vs GPU Performance

Wolf Defender is a ModernBERT-based prompt-injection classifier (~1.2GB). During the OWASP scan, Wolf was migrated from CPU to GPU mid-job — this was a single continuous EvalHub/Garak job that was never restarted. The Wolf InferenceService URL stayed the same; only the backing deployment was swapped from vLLM x86 (7 CPU replicas) to vLLM CUDA (1 GPU replica on L4). Garak runs probes sequentially, so the two phases processed different probes with different prompts — the first ~4,332 classification requests hit CPU (including DAN probes, which caused timeouts), while the remaining ~8,662 requests hit GPU. This is not a controlled A/B test — it is a real-world infrastructure migration under live scan load. The latency comparison (same model, same endpoint, different hardware) is valid, but note that different probes generate different prompt lengths.

On CPU, long DAN prompts took 15-20s per classification, causing NemoGuardrails' 60s timeout to fire. This created a death spiral:

Wolf timeout → NemoGuardrails error → proxy 502 → garak retry → more Wolf load → repeat

Result: After the mid-scan GPU migration, all timeouts stopped. A single L4 GPU handled 2x more requests than 7 CPU replicas combined, with classification latency dropping from seconds to sub-second. The Garak scan generated far higher concurrent load than a typical production workload. CPU deployment may be viable for lower-intensity use cases — but GPU delivers tangible 17x latency benefits worth considering depending on your concurrency and latency requirements.

Caveat: Because this was a mid-scan swap (not a controlled experiment), the CPU and GPU phases processed different Garak probes with different prompts. The latency improvement is real (same classifier, same endpoint, different hardware), but the exact 17x figure reflects the specific prompt mix each phase received.

Post-analysis of the full 24,090-attempt dataset confirmed: 0% actual guardrailed ASR — all non-zero raw ASR was caused by the NemoGuardrails stop parameter bug. Full scan completed in 24 minutes.
