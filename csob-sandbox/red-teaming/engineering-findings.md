# EvalHub Engineering Findings -- RHOAI 3.5

**Author:** Anton Giertli, Senior Solution Architect, Red Hat  
**Date:** October 2026  
**Customer:** ČSOB (Československá obchodná banka)  
**Environment:** RHOAI 3.5 Self-Managed, EvalHub with Garak provider  
**Model under test:** Gemma 4 12B (served via vLLM on KServe)

---

## Summary

During red-teaming evaluation of an LLM deployment for the ČSOB banking sandbox, we encountered several issues with the EvalHub/TrustyAI platform that affect production readiness. The findings range from a critical networking bug that blocks all `intents` (garak-kfp) scans, to UX gaps that undermine user trust in scan results.

46 evaluation jobs were submitted across OWASP LLM Top 10 and Intents benchmarks, testing both raw (unguarded) and guardrailed (Wolf Defender, Granite Guardian 8B) configurations. **22 of 46 jobs (48%) show as "Failed" in the UI despite the underlying garak scans completing successfully.** Results had to be manually recovered from S3 artifacts.

## Finding 1: DSPA NetworkPolicy Blocks EvalHub Pods

**Severity:** CRITICAL  
**Affects:** All `intents` (garak-kfp) scans  
**Reproducible:** Yes, 100% of the time

### Impact

ALL intents (garak-kfp) jobs get stuck in "running" state indefinitely or are eventually marked "Failed". EvalHub cannot poll DSPA for pipeline status.

### Root Cause

The DSPA operator auto-generates a `NetworkPolicy` named `ds-pipelines-dspa` in the project namespace (e.g., `csob-sandbox`). This policy restricts ingress to pods matching specific label selectors:

```yaml
# Auto-generated by DSPA operator
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ds-pipelines-dspa
  namespace: csob-sandbox
spec:
  podSelector:
    matchLabels:
      app: ds-pipeline-dspa
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: ds-pipeline-dspa
        - podSelector:
            matchLabels:
              component: data-science-pipelines
```

The EvalHub API pod has label `app: eval-hub` -- it does not match any allowed selector. Network traffic from the EvalHub pod to the DSPA API endpoint is silently dropped.

### Symptoms

1. EvalHub submits the pipeline run to DSPA successfully (the pipeline pods run and complete normally)
2. EvalHub attempts to poll DSPA for status updates on port 8888 (HTTPS) -- connection times out
3. Job stays in "running" state forever in the Evaluations UI
4. If EvalHub pod restarts (e.g., due to OOM or rolling update), it retries the status check, gets connection timeout, and marks the job as "Failed"

### Verification

```bash
# Check the auto-generated NetworkPolicy
oc get networkpolicy ds-pipelines-dspa -n csob-sandbox -o yaml

# Check EvalHub pod labels (note: app=eval-hub, NOT app=ds-pipeline-dspa)
oc get pods -n csob-sandbox -l app=eval-hub --show-labels

# Check garak job pod labels
oc get pods -n csob-sandbox -l component=evaluation-job --show-labels
```

### Fix (workaround)

Create a supplementary NetworkPolicy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-evalhub-to-dspa
  namespace: csob-sandbox
spec:
  podSelector:
    matchLabels:
      app: ds-pipeline-dspa
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: eval-hub
        - podSelector:
            matchLabels:
              component: evaluation-job
      ports:
        - protocol: TCP
          port: 8888   # DSPA HTTPS API
        - protocol: TCP
          port: 8887   # DSPA gRPC
```

### Recommendation

The DSPA operator should include EvalHub pods in its auto-generated NetworkPolicy, or the EvalHub operator should create this supplementary policy when it detects a DSPA in the same namespace.

## Finding 2: MLflow runID Propagation Failure in garak-kfp Pipelines

**Severity:** HIGH  
**Affects:** MLflow integration for intents scans (garak-kfp provider)  
**Reproducible:** Yes, on every intents scan with MLflow enabled

### Impact

MLflow integration does not save results for `intents` scans submitted via the garak-kfp provider. Scan results must be manually recovered from S3.

### Error

Pipeline logs show:

```
runID is required to update nested MLflow run
```

### Context

The EvalHub MLflow integration flow for garak-kfp:

1. EvalHub creates an MLflow **parent run** in the configured experiment
2. EvalHub passes the `runID` of the parent run to the garak-kfp pipeline as a parameter
3. The pipeline's MLflow handler attempts to create a **nested run** under the parent
4. The handler fails because the `runID` was not correctly propagated through the KFP pipeline parameter chain

### Result

- The garak scan itself completes successfully (results uploaded to S3, HTML report generated in the pipeline pod)
- The MLflow handler failure may poison the pipeline exit status, contributing to Finding 3
- No metrics, params, or artifacts land in MLflow for the scan

### Verification

```bash
# Check pipeline run logs for the MLflow handler step
oc logs -n csob-sandbox <garak-kfp-pod> -c main | grep -i "runID"

# Check if MLflow parent run exists but has no nested runs
# (requires MLflow UI or API access)
```

### Recommendation

1. The MLflow handler failure should **not** affect the overall pipeline status. Garak scan success should be the primary status indicator.
2. The runID propagation mechanism should be tested end-to-end for garak-kfp pipelines specifically (the OWASP/garak provider path may work differently).

## Finding 3: Job Status Poisoning -- Pipeline Success != Job Success

**Severity:** HIGH  
**Affects:** All scan types, particularly intents (garak-kfp)  
**Reproducible:** Yes

### Impact

22 of 46 jobs (48%) show as "Failed" in the Evaluations UI, even when the underlying garak scan completed successfully and produced valid results.

### Evidence

Side-by-side comparison of the same scan:

| View | Status | Data shown |
|------|--------|------------|
| **Evaluations** (`/evaluations`) | Failed | No result, no error message |
| **Pipeline Runs** (`/develop-train/runs/csob-sandbox`) | Complete | `attack_success_rate: 2.63` |

The Pipeline Runs view correctly shows the run as "Complete" with valid metrics. The Evaluations view shows the same job as "Failed" with no actionable information.

### Root Cause

Combination of:
- **Finding 1** (NetworkPolicy blocking status polling): EvalHub cannot reach DSPA to check pipeline status, so it marks the job as failed after timeout
- **Finding 2** (MLflow handler failure): Even when the network issue is resolved, the MLflow handler failure in the pipeline may poison the exit status that EvalHub reads

Either failure alone is sufficient to mark the job as "Failed", even when the garak scan itself succeeded.

### Recommendation

1. EvalHub should distinguish between:
   - **Scan failed** -- garak returned an error, no results produced
   - **Infrastructure failure** -- couldn't reach DSPA, MLflow write failed, etc.
   - **Scan succeeded with warnings** -- garak completed but ancillary steps (MLflow, status polling) failed
2. At minimum, if the pipeline completed successfully in KFP, the Evaluations job should reflect that and surface the results
3. Failed jobs should display the specific error message, not just "Failed"

## Finding 4: UI Navigation Gap -- No Cross-Linking Between Views

**Severity:** MEDIUM  
**Affects:** Usability for all users  

### Impact

Users cannot trace from a failed Evaluation to its actual pipeline results. Diagnosing failures requires manual navigation across 4 disconnected UI views.

### Details

The RHOAI dashboard has 4 views that contain evaluation-related data, but none of them link to each other:

| # | View | URL path | What it shows | Missing |
|---|------|----------|---------------|---------|
| 1 | **Experiments** (MLflow) | `/experiments` | Experiment names, tags, MLflow runs | No link to Evaluations |
| 2 | **Evaluations** | `/evaluations` | Job status (Failed/Cancelled/Complete) | Cannot drill into Failed jobs. No link to Pipeline Run. No error message. |
| 3 | **Artifacts** | `/artifacts` | Raw S3 blobs (`executor-logs`, `taxonomy_dataset`, `sdg_dataset`) | No evaluation context. User cannot tell which artifact belongs to which evaluation. |
| 4 | **Runs** | `/develop-train/runs/<project>` | KFP pipeline steps, `attack_success_rate` column | No way to navigate here FROM Evaluations |

### User Journey (current)

1. User sees "Failed" in Evaluations
2. User has no idea why it failed -- no error message, no link
3. User must manually navigate to Pipeline Runs, guess which run corresponds to the evaluation
4. If they find the run, it may show "Complete" with valid results -- contradicting the "Failed" status
5. To get artifacts, user must go to yet another view and guess which S3 blob belongs to the scan

### Recommendation

1. Add cross-links: Evaluation -> Pipeline Run -> Artifacts
2. At minimum, clicking a Failed evaluation should show:
   - The specific error message
   - A link to the underlying KFP pipeline run
   - A link to any artifacts produced (even if the job "failed")

## Finding 5: ASR Discrepancy -- Routing Path Affects Results

**Severity:** LOW  
**Affects:** Result consistency  

### Impact

Same benchmark (OWASP LLM Top 10), same model (Gemma 4 12B), two different ASR results depending on the network routing path:

| Routing path | ASR | Scan date |
|-------------|-----|-----------|
| via `maas-auth-proxy` -> `gemma-pool` | **24.67%** | Earlier scan |
| Direct to `gemma-pool` service | **6.51%** | Verification scan |

### Context

- The 24.67% result came from a scan where the model was accessed through `maas-auth-proxy` (a sidecar proxy that handles MaaS authentication before forwarding to the model service)
- The 6.51% result came from a later verification scan that hit `gemma-pool` directly (bypassing the proxy)
- The proxy may introduce latency, modify HTTP headers, or affect streaming/chunked response behavior in ways that change how garak's attack probes interact with the model

### Note

This may not be a bug -- it is plausible that different network paths (with different latency characteristics, header handling, and connection behavior) produce legitimately different results. However, a 4x difference in ASR is surprising and warrants investigation into whether the proxy is introducing artifacts that affect garak's probe evaluation logic.

### Verification

```bash
# Check proxy routing
oc get svc maas-auth-proxy -n csob-sandbox -o yaml
oc get svc gemma-pool -n csob-sandbox -o yaml

# Compare response headers between direct and proxied requests
curl -sk https://gemma-pool.csob-sandbox.svc:8000/v1/models -H "Authorization: Bearer $TOKEN"
curl -sk https://maas-auth-proxy.csob-sandbox.svc:8080/v1/models -H "Authorization: Bearer $TOKEN"
```

## Finding 6: EvalHub API Cannot Delete Running/Failed Jobs (HTTP 409)

**Severity:** MEDIUM  
**Affects:** Operational hygiene, UI clutter  
**Reproducible:** Yes, 100%

### Impact

Once an EvalHub evaluation job transitions to `running` or `failed` state, the API refuses to delete it with HTTP 409 Conflict. This leads to zombie entries in the Evaluations UI that can only be removed by directly deleting rows from the PostgreSQL database.

### Root Cause

The EvalHub API enforces state-based delete restrictions. A job in `running` state cannot be deleted even if the eval pod was killed (orphaned job). A job in `failed` state also cannot be deleted in many cases. The cancel event endpoint (`POST /jobs/{id}/events` with `status: cancelled`) returns 400 — the cancellation event format may differ from what the API expects.

### Reproduction

```bash
# Submit a job, let it start running, then kill the eval pod
oc delete pod <eval-pod> -n csob-sandbox --force --grace-period=0

# Try to delete the orphaned job — returns 409
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
curl -sk -X DELETE "https://evalhub:8443/api/v1/evaluations/jobs/<job-id>" \
  -H "Authorization: Bearer $TOKEN" -H "X-Tenant: csob-sandbox"
# HTTP 409 Conflict
```

### Workaround

Delete directly from PostgreSQL:
```bash
oc exec <evalhub-postgres-pod> -n csob-sandbox -- \
  psql -U evalhub -d evalhub -c "DELETE FROM evaluations WHERE id NOT IN ('<keep-id-1>','<keep-id-2>');"
```

### Recommendation

1. Add a `force=true` query parameter to the DELETE endpoint that bypasses state checks
2. Add a TTL-based cleanup for jobs in `running` state with no corresponding eval pod
3. At minimum, expose a "Delete" action in the Evaluations UI for failed/cancelled jobs

## Finding 7: kube-rbac-proxy Missing MLflow Experiment Create Permission

**Severity:** HIGH  
**Affects:** All scan submissions via in-cluster Jobs (kustomize/Helm automated scans)  
**Reproducible:** Yes, 100%

### Impact

Scan submission Jobs using the default ServiceAccount get HTTP 403 from EvalHub's kube-rbac-proxy:

```
Forbidden (user=system:serviceaccount:csob-sandbox:default, verb=create, resource=experiments, subresource=)
```

The operator-created `evalhub-tenant-admin` Role only grants `get, list` on `mlflow.kubeflow.org/experiments`, but the kube-rbac-proxy auth config requires `create` for POST to `/api/v1/evaluations/jobs`.

### Root Cause

The kube-rbac-proxy config (`auth.yaml`) maps POST `/api/v1/evaluations/jobs` to THREE SubjectAccessReview checks:
1. `trustyai.opendatahub.io/evaluations:create` — granted by `evalhub-tenant-admin`
2. `mlflow.kubeflow.org/experiments:create` — **NOT granted**
3. `mlflow.kubeflow.org/experiments:get` — granted by `evalhub-tenant-admin`

All three must pass. The missing `create` verb on `experiments` causes 403 for ALL ServiceAccount-based scan submissions.

### Workaround

Create a supplementary Role:
```bash
oc create role evalhub-mlflow-experiment-create -n csob-sandbox \
  --verb=create,get,list --resource=experiments --resource-group=mlflow.kubeflow.org
oc create rolebinding evalhub-mlflow-experiment-create-binding -n csob-sandbox \
  --role=evalhub-mlflow-experiment-create --group=system:serviceaccounts:csob-sandbox
```

### Recommendation

The `evalhub-tenant-admin` Role should include `create` on `mlflow.kubeflow.org/experiments` to match the kube-rbac-proxy auth config requirements.

## Finding 8: LiteLLM SDG Step Requires Provider-Prefixed Model Name

**Severity:** HIGH  
**Affects:** All intents (garak-kfp) scans using self-hosted models  
**Reproducible:** Yes, 100%

### Impact

The garak-kfp intents pipeline `sdg-generate` step crashes within seconds:

```
litellm.BadRequestError: LLM Provider NOT provided. Pass in the LLM provider
you are trying to call. You passed model=gemma-4-12b
```

This causes the KFP pipeline run to FAIL, which causes the eval pod to report FAILED, which pollutes the Evaluations UI with failed entries.

### Root Cause

The SDG step uses LiteLLM internally for model inference. LiteLLM requires a provider prefix (e.g., `openai/gemma-4-12b`) when using a custom `api_base` URL. Bare model names like `gemma-4-12b` fail because LiteLLM cannot determine which provider format to use.

The `intents_models.sdg.name` and `intents_models.judge.name` fields in the EvalHub API payload must use the LiteLLM provider prefix.

### Working Configuration

```json
"intents_models": {
  "judge": {"url": "http://gemma-pool:8000/v1", "name": "openai/gemma-4-12b"},
  "sdg": {"url": "http://gemma-pool:8000/v1", "name": "openai/gemma-4-12b"}
}
```

For external MaaS endpoints, use the appropriate LiteLLM prefix (e.g., `hosted_vllm/qwen36-35b-a3b`).

### Recommendation

EvalHub should auto-prefix model names with `openai/` when a custom `api_base` is provided and no prefix is present, since the vast majority of self-hosted vLLM endpoints are OpenAI-compatible.

## Finding 9: Scan Results Summary

**Severity:** INFO  
**Purpose:** Reference data from completed scans

### OWASP LLM Top 10 (garak provider)

| Variant | ASR | Guardrail | Notes |
|---------|-----|-----------|-------|
| Raw (via proxy) | **24.67%** | None | Earlier scan, routed through `maas-auth-proxy` |
| Raw (direct) | **6.51%** | None | Verification scan, direct to `gemma-pool` |
| Guardrailed | **4.88%** | Wolf Defender (embedded) | **80.2% relative reduction** vs 24.67% raw |
| Guardrailed | **10.18%** | Granite Guardian 8B (external) | Worse than Wolf Defender for this benchmark |

### Intents (garak-kfp provider)

| Variant | ASR | Duration | Guardrail | Notes |
|---------|-----|----------|-----------|-------|
| Raw | **0--2.63%** | ~4 hours | None | Gemma 4 12B has strong built-in safety |
| Guardrailed | **0--2.63%** | ~4 hours | Wolf Defender | Minimal delta -- base model already safe for intents |

### Analysis

- **OWASP attacks** (prompt injection, jailbreaking): Wolf Defender provides significant protection. Gemma 4 12B's built-in alignment is insufficient -- 24.67% ASR means roughly 1 in 4 OWASP attacks succeed against the raw model.
- **Intent-based attacks** (SPO probes, TAP): Gemma 4 12B has robust built-in alignment. ASR is already near zero without guardrails, so Wolf Defender adds minimal incremental value for this attack category.
- **Wolf Defender vs Granite Guardian 8B**: Wolf Defender (4.88% ASR) outperforms Granite Guardian 8B (10.18% ASR) on the OWASP benchmark for this model. Wolf Defender's embedded architecture (no separate inference call) also has lower latency overhead.
