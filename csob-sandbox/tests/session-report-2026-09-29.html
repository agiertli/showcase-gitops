Translation and TAP strategies disabled

Translation attacks (Mandarin Chinese) require pre-downloaded Helsinki-NLP models. TAP (Tree of Attacks with Pruning) requires a dedicated attacker model. Both disabled for initial PoC to reduce complexity. Can be enabled later.

Expected Results

Raw vLLM: Higher ASR — gemma-4-12b has built-in RLHF safety training, but SPO strategies can often bypass it by replacing the system prompt entirely.

GuardRails: Near-zero ASR — the Wolf Defender ML classifier intercepts prompt injection before the prompt reaches the LLM. The classifier operates on the raw input text, so system prompt overrides and augmented prompts are still detected as injection attempts.

Key metric: ASR (Attack Success Rate) = % of unique prompts that bypassed safety controls under any strategy. Lower is better. Score above 0.5 = evaluation threshold exceeded.

Key Decisions & Findings

Garak initially deferred — too many dependencies for one day
EvalHub + DSPA + judge/SDG models. Revisited after discovering MaaS RHDP access.
MaaS RHDP models solve the auxiliary model problem
qwen36-35b-a3b (judge — direct vLLM, no rate limits) and gpt-oss-120b (SDG — LiteLLM proxy to Vertex AI, may rate-limit at 429). Using the target model as its own judge was scientifically weak — separate models make the evaluation credible.
vllm-cpu-x86-runtime must be created manually for CLI/gitops deployments
RHOAI 3.5 ships it as a dashboard template (ConfigMap), not a pre-deployed ClusterServingRuntime. The manifest is needed in gitops repos. HF Detector runtime was deliberately avoided due to library incompatibility with Wolf Defender.
imagePullPolicy: Always is NOT set by RHOAI
Customer reported vLLM CUDA images using Always pull policy. Investigation showed: DSC has no imagePullPolicy knob, inferenceservice-config deploy section doesn't set it, all pods on our cluster show IfNotPresent. Customer's cluster likely has a mutating admission webhook enforcing Always — common bank security policy. For digest-pinned images this adds no security value.
NemoGuardrails is CLI/YAML only — no dashboard UI
No RHOAI dashboard support for creating or managing NemoGuardrails CRs. Configuration is entirely via oc apply.

Deployment Steps (On-Site)

Prerequisites: RHOAI 3.5 installed, TrustyAI Managed in DSC, GPU node available, guardrails already deployed and tested (14/14).

Estimated time: 2-3 hours (deploy infrastructure + run scans + wait for results)
  1. Deploy MinIO: oc apply -f argo-apps/rhoai-config/minio-namespace.yaml && oc apply -f argo-apps/rhoai-config/minio.yaml
  2. Create S3 bucket: oc exec -n minio deploy/minio -- mc alias set local http://localhost:9000 minio minio123 && mc mb local/garak-pipeline
  3. Apply red-teaming manifests: oc apply -f csob-sandbox/red-teaming/ --server-side
  4. Wait for EvalHub pod Running + DSPA Ready
  5. Patch API key: source .env && oc patch secret maas-rhdp-api-key -n csob-sandbox --type merge -p '{"stringData":{"API_KEY":"'$MAAS_RHDP_API_KEY'"}}'
  6. Run scans: ./csob-sandbox/red-teaming/run-scans.sh
  7. Wait for completion (check job status via EvalHub API)
  8. Compare ASR between raw and guardrailed endpoints
